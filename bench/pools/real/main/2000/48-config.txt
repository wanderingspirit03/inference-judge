Our seed bank's nightly backup has been "working" for two years, but last week a restore test failed and nobody can say why. Please audit these files like a careful sysadmin: list every problem you find in order of seriousness, explain why each one matters for us, and then give me a corrected version of the script and the timer files. I'm not a shell expert, so keep the explanations clear.

Context: Fernhollow Seed Bank keeps its accession records (about 48,000 rows) in a PostgreSQL database on the host `vault01`, and scanned packet photos in /srv/seedphotos (roughly 90 GB). The backup copies both to the NAS at /mnt/nas/backups and to an offsite bucket.

--- /usr/local/bin/seedbackup.sh ---

#!/bin/bash
# nightly backup for seed bank
# written by Odile, 2023

DB=accessions
USER=seedadmin
PASS=Gr33nhouse2023
DEST=/mnt/nas/backups
DATE=`date +%d-%m-%Y`
LOG=/var/log/seedbackup.log
KEEP=14

echo "backup started $DATE" >> $LOG

cd $DEST

# dump the database
PGPASSWORD=$PASS pg_dump -U $USER $DB > $DEST/db-$DATE.sql
if [ $? -ne 0 ]
then
  echo "dump failed" >> $LOG
fi

# compress it
gzip $DEST/db-$DATE.sql

# photos
rsync -av --delete /srv/seedphotos/ $DEST/photos/ >> $LOG 2>&1

# keep only the last $KEEP days of dumps
find $DEST -name "db-*.sql.gz" -mtime +$KEEP -exec rm {} \;

# offsite copy
export AWS_ACCESS_KEY_ID=AKIAEXAMPLE0000FERN
export AWS_SECRET_ACCESS_KEY=example-secret-not-real-0000
aws s3 sync $DEST s3://fernhollow-offsite-2023 --quiet

# check free space
FREE=`df $DEST | tail -1 | awk '{print $4}'`
if [ $FREE -lt 50000000 ]
then
  echo "low space" | mail -s "backup space" admin@example.org
fi

echo "backup finished" >> $LOG

--- /etc/systemd/system/seedbackup.service ---

Notes from the restore test (Thursday, done by Wilhelmina):
- The newest dump file db-12-10-2026.sql.gz was only 20 KB. The ones from a few weeks ago are around 310 MB.
- When she unpacked it, it contained a single line: "pg_dump: error: connection to server on socket failed: FATAL: password authentication failed for user seedadmin".
- The log says "backup started 12-10-2026", then "dump failed", then the rsync output, then "backup finished". Nobody read it.
- The NAS had been remounted after a power cut on the 3rd and was mounted read-only for a while. The photos folder on it has not changed since then, and the rsync lines in the log show "Read-only file system" errors for those days.
- The database password was changed by the IT contractor last month, and he told Odile, who has since left.
- The offsite bucket has no lifecycle rules and is now 1.9 TB, though the live data is about 90 GB plus 15 GB of dumps.
- The sync of the whole backup folder goes up every night, including dumps that are removed locally. Because the sync does not use the delete flag, the bucket keeps every dump ever made.
- The server's clock is set to local time. In March 2026 the timer fired twice on the night the clocks changed, according to Wilhelmina.
- We also have a cron file that does the same rsync of the photos at 02:00 as the timer does, so the two jobs run at the same moment.
- Nobody has a record of where the offsite bucket credentials were created, and the same key pair is also used by the website upload form.
- The monthly tidy job is meant to remove thumbnails only. Last month Wilhelmina noticed that a few full size photos with the word "thumb" in the file name, such as 4471-thumbnail-study.tif, went missing.
