It runs our member portal (hive registrations, apiary visit bookings, the swarm-collection phone list) and a small collector for sensor data from members' hive scales. Could you audit these files properly? I'd like a list of the problems ordered by how serious they are, an explanation of why each one matters, and then a corrected version of every file. Keep it simple enough that the next volunteer can understand it.

```bash

# nightly backup, runs from root's crontab at 03:00
# 0 3 * * * /srv/portal/backup.sh
```

--- collector/collect.py ---

```python
import json
import os
import time

import paho.mqtt.client as mqtt
import psycopg2

conn = psycopg2.connect(os.environ["DATABASE_URL"])
cur = conn.cursor()


def on_message(client, userdata, msg):
    data = json.loads(msg.payload)
    print("got", data)
    cur.execute(
        "INSERT INTO readings (scale_id, weight_kg, temp_c, recorded_at) VALUES ('%s', %s, %s, now())"
        % (data["scale"], data["weight"], data["temp"])
    )
    conn.commit()


client = mqtt.Client()
client.username_pw_set(os.environ["MQTT_USER"], os.environ["MQTT_PASSWORD"])
client.on_message = on_message
client.connect(os.environ["MQTT_HOST"], 1883)
client.subscribe("scales/#")

while True:
    try:
        client.loop_forever()
    except Exception as e:
        print(e)
        time.sleep(5)
```

--- notes on the database from the old README ---

```text
- Postgres runs with default settings. The only tuning done was by the previous
  volunteer: shared_buffers = 4GB (the VPS has 2 GB of RAM) and max_connections = 500.
- The readings table has no index except the primary key. The "my hives" page in the
  portal takes about 9 seconds to load for members who have more than 3 scales.
- Passwords of the 340 member accounts were stored with an unsalted hash of the
  password until last year, when the new login code was added. Old accounts that have
  not logged in since still have the old hash.
- Uploaded photos of hives and swarm sightings are stored in /app/uploads inside the
  container. They are not in the backup and are lost when the container is rebuilt.
```

--- logrotate and cron notes (from the old README) ---

```text
- Logs from gunicorn go to stdout, docker keeps them forever. Last time the disk
  filled up in February we deleted /var/lib/docker/containers/*/*.log by hand.
- Certificates: we used to run certbot by hand every three months. Nobody has done
  it since the previous volunteer left. The portal is currently reachable on port 80
  only. Members have been told to ignore the browser warning.
- The collector restarts itself when the MQTT broker goes down, so there is no
  alerting. If hive weights stop appearing, ask Tomas to restart the VPS.
- Server login is root with a password that is kept in the shared document that all
  committee members can read.
```

Some context on how things are used. The portal has about 340 accounts and gets most of its traffic in April and May, when swarm season starts and members book apiary visits. Hive scale readings arrive every 15 minutes from about 60 scales. Members' postal addresses and phone numbers are in the database, so I am nervous about losing it or leaking it. The only deployment that ever happens is when I push to the main branch; sometimes I push on a Saturday evening and the site is down for a minute or two while it rebuilds. We have no staging copy. The association pays about 12 euros per month for the VPS and nothing for the storage bucket, which is a free tier of 5 GB. The database file is currently 380 MB and grows by about 40 MB a month because of the scale readings.
